Descripción general

Explicación breve del objetivo del proyecto, del problema que resuelve y de sus dos formas principales de uso.

SmartFenix es una aplicación desarrollada con Spring Boot para gestionar clientes, empleados, proyectos y tareas de una forma más organizada. La idea principal del proyecto es reunir en una sola aplicación información que normalmente estaría repartida en distintos sitios, de manera que sea más fácil consultarla, modificarla y comprobar su estado.

El proyecto resuelve el problema de llevar el control de datos empresariales de forma desordenada. En lugar de depender de herramientas separadas, SmartFenix permite centralizar clientes o empresas, empleados internos, proyectos asociados a un cliente y tareas asignadas a proyectos y empleados.

Desde la aplicación, el usuario puede crear registros nuevos, consultar información guardada, modificar datos existentes y eliminar registros cuando sea necesario. La interfaz web con Thymeleaf está pensada para trabajar desde el navegador, mientras que la API REST está pensada para realizar peticiones HTTP desde herramientas como Postman o desde pruebas automáticas.

Arquitectura del sistema

La aplicación sigue una arquitectura por capas para separar responsabilidades y facilitar mantenimiento, pruebas y comprensión del flujo interno.

Capas principales

Domain: contiene las entidades JPA y representa la estructura principal de los datos.

Repository: contiene interfaces que extienden JpaRepository y permiten guardar, buscar, listar y eliminar registros.

Service: concentra la lógica de negocio y evita que el controlador acceda directamente al repositorio.

Controller: recibe peticiones HTTP y devuelve vistas web o respuestas JSON.

Depuración del sistema

La depuración ayuda a entender el flujo interno del programa y a revisar cómo cambian los valores durante la ejecución. El caso principal recomendado es la eliminación de un cliente con proyectos asociados.

  1. Poner breakpoints en ClienteWebController.eliminar(...) y ClienteService.delete(...).
  2. Arrancar la aplicación y entrar en http://localhost:8099/clientes.
  3. Intentar eliminar un cliente con proyectos asociados.
  4. Avanzar paso a paso con Step Over.
  5. Inspeccionar id, la comprobación de existencia, la comprobación de proyectos asociados y la excepción controlada.
  6. Comprobar que la web muestra un mensaje controlado y no aparece error 500.

Eliminación controlada de registros relacionados

Durante las pruebas se detectó que algunos registros no podían eliminarse directamente porque estaban relacionados con otras entidades. Esto ocurre por las claves foráneas de la base de datos, que protegen la integridad de la información.

Casos detectados

Un cliente no puede eliminarse si tiene proyectos asociados.

Un empleado no puede eliminarse si tiene tareas asignadas.

Un proyecto no puede eliminarse si tiene tareas asociadas.

Solución aplicada

Comprobar si existen registros relacionados antes de eliminar.

Bloquear la eliminación si existen dependencias.

Mostrar mensajes claros en web y respuestas controladas en la API.

RegistroDependencia revisadaResultado si tiene dependenciaResultado si no tiene dependencia
ClienteProyectos asociadosNo se elimina y se muestra mensaje.Se elimina correctamente.
EmpleadoTareas asignadasNo se elimina y se muestra mensaje.Se elimina correctamente.
ProyectoTareas asociadasNo se elimina y se muestra mensaje.Se elimina correctamente.
TareaSin dependencias principalesSe elimina normalmente.Se elimina correctamente.

Verificación de DELETE en web y API

Se comprobó el comportamiento real tanto desde la interfaz web como desde la API REST para asegurar que los errores quedan controlados y que los borrados válidos se completan correctamente.

Interfaz web

Desde los listados se verificó que el usuario puede intentar eliminar registros y recibir siempre una respuesta controlada.

  • Si el registro tiene relaciones, aparece un mensaje claro.
  • Si el registro no tiene relaciones, se elimina correctamente.
  • No aparece Whitelabel Error Page.
  • No aparece error 500.

API REST

SituaciónCódigo HTTPSignificado
Eliminación correcta204 No ContentEl registro se ha eliminado.
Registro inexistente404 Not FoundEl ID no existe.
Registro con dependencias409 ConflictNo se puede eliminar por relaciones existentes.

Pruebas validadas

Conflictos controlados: DELETE /api/clientes/1, DELETE /api/empleados/1 y DELETE /api/proyectos/2 devolvieron 409 Conflict.

Eliminaciones correctas: DELETE /api/tareas/1, DELETE /api/empleados/1, DELETE /api/proyectos/1 y DELETE /api/clientes/1 devolvieron 204 No Content cuando ya no existían dependencias.

Registro inexistente: un segundo DELETE /api/tareas/1 devolvió 404 Not Found.

Conclusión

Cierre final de la memoria y relación del proyecto con el resultado de aprendizaje trabajado.

Con este proyecto se aprende que verificar una aplicación no consiste solo en mirar si arranca, sino en comprobar de forma ordenada que cada parte funciona como debe. A través de los casos de prueba, las pruebas unitarias, la prueba de integración y la depuración, se puede justificar mejor que el sistema responde correctamente.

Las pruebas ayudan a detectar errores antes de la entrega y permiten trabajar con más seguridad. También es importante separar las pruebas unitarias de las de integración, porque cada una revisa una parte distinta del proyecto.

La depuración con IntelliJ también ayuda mucho a entender el flujo interno del programa, porque permite ver paso a paso qué hace cada método y cómo cambian los datos. Además, la verificación final ha permitido detectar y corregir un error real de serialización en la API REST.

Por todo esto, SmartFenix cumple mejor el resultado de aprendizaje RA3, ya que se han comprobado casos normales y casos de error, la aplicación gestiona correctamente restricciones de base de datos y la eliminación de datos se realiza de forma segura.
